# Apex — 통합 게임 계획서 v2.0

- 문서 상태: Pre-Production
- 장르: 온라인 경쟁 레이싱 + 차량 제작/세팅
- 핵심 경쟁 방식: 상시 ELO 기반 개인전 (최대 8인)
- 개발 방식: **100% 바이브 코딩** — 사람은 GUI 에디터를 쓰지 않는다. 모든 산출물은 AI가 텍스트(코드/설정/데이터)로 생성하고, 사람은 방향 제시와 플레이 피드백만 담당한다.
- 이 문서는 구 `PRD.md`(v1.2)와 구 `PRODUCTION_PLAN.md`(v1.0)를 대체한다. **이 문서 하나만으로 게임 전체를 제작할 수 있어야 한다.**

# PART 0. 문서 운영 규칙

1. 이 문서가 게임의 **유일한 명세 원천**이다. 코드/데이터와 이 문서가 충돌하면 이 문서가 옳다. 단, 튜닝으로 수치를 바꿀 때는 **같은 커밋에서 이 문서의 해당 수치도 함께 갱신**한다.
2. 수치는 세 종류로 구분한다.
   - **[확정]** 설계 원칙이라 바꾸지 않는 값 (예: 최대 8인, 서버 권위).
   - **[초기값]** 구현 시작점. 밸런스 스윕/플레이 피드백으로 튜닝 대상. 변경 시 문서 갱신.
   - **[목표]** 구현 결과가 만족해야 하는 수용 기준. 자동 테스트로 검증한다.
3. 새 기능은 이 문서에 먼저 추가한 뒤 구현한다. 문서에 없는 기능을 AI가 임의로 추가하지 않는다.
4. 문서 언어는 한국어, 코드/식별자/커밋/로그/에러 메시지는 영어다.
5. 용어 표기: 게임 내 영문 고정 용어(Qualifying, Grand Prix, Engineer 등)는 영어 그대로 쓰고, UI 노출 문구는 i18n 키(`ko`, `en`)로만 관리한다.

# PART 1. 제품 정의

## 1.1 한 줄 정의

매칭이 잡힌 순간 공개되는 트랙에 맞춰 자신의 레이싱 머신을 즉석에서 준비하고, 퀄리파잉과 그랑프리를 거쳐 실력에 따라 ELO를 올리는 온라인 경쟁 레이싱 게임.

## 1.2 핵심 정체성

플레이어는 단순히 자동차를 운전하지 않는다. **차량 제작 + 차량 세팅 + 트랙 분석 + 퀄리파잉 + 레이스 전략 + 실제 운전**을 모두 수행한다.

핵심 재미: **"이번 트랙에서 어떤 차를 준비하고 어떻게 달릴 것인가?"**

방향성: 카트라이더의 접근성 + F1의 레이스 구조/전략 + 차량 제작/세팅 시스템.

## 1.3 핵심 문장

> **"매칭이 잡히기 전에는 아무도 이번 레이스를 완벽하게 준비할 수 없다."**

트랙이 공개되는 순간 플레이어는 판단해야 한다. 어떤 부품을 장착할 것인가? 어떤 타이어를 사용할 것인가? 다운포스를 얼마나 줄 것인가? 예선에서 얼마나 공격적으로 달릴 것인가? 승패를 결정하는 것은 **차량 설계 + 순간적인 세팅 판단 + 전략 + 운전 실력**이다.

## 1.4 설계 원칙 (7)

1. **운전이 가장 중요하다** — 세팅이 아무리 좋아도 운전을 못하면 이길 수 없어야 한다.
2. **차량 세팅은 차이를 만든다** — 하지만 세팅만으로 승패가 결정되어서는 안 된다.
3. **트랙은 매칭 이후 공개한다** — 매 판 즉석 판단을 만든다.
4. **ELO는 지속된다** — 강제 시즌 리셋을 하지 않는다.
5. **콘텐츠 시즌과 경쟁 랭킹을 분리한다.**
6. **RNG는 통제한다** — 피트/충돌/출발 등 중요한 결과가 단순 운으로 결정되지 않게 한다. 필요한 난수는 서버가 매치 시드로 생성해 전원에게 동일하게 적용한다.
7. **Pay-to-Win을 방지한다** — 돈을 많이 쓴 플레이어가 ELO를 쉽게 올릴 수 있는 구조를 만들지 않는다.

## 1.5 전체 게임 루프

```
게임 접속 → 경쟁전 선택 → 매칭 시작 → 매칭 완료 → 트랙 공개 → 준비 시간
→ 부품 교체 / 차량 세팅 / 스킨 변경 → 준비 완료 → 퀄리파잉 → 출발 그리드 결정
→ 그랑프리 → 최종 순위 → ELO 계산 → 결과 → 다음 매칭
```

## 1.6 최종 제품 정의

이 게임의 경쟁 구조는 시즌을 끝내기 위해 달리는 구조가 아니다. 플레이어는 언제든지 경쟁전에 들어가고, 매칭 → 트랙 공개 → 차량 준비 → 퀄리파잉 → 그랑프리를 하나의 완결된 경쟁 경험으로 즐긴다. 장기 목표는 시즌 포인트가 아니라 **"내 ELO를 어디까지 올릴 수 있는가?"** 이다. 콘텐츠 시즌은 경쟁 랭킹을 초기화하기 위한 장치가 아니라 새로운 트랙, 부품, 스킨, 이벤트를 공급하는 라이브 콘텐츠 구조로만 사용한다.

# PART 3. 코딩 수칙 (CLAUDE.md의 원문)

Stage 0.1에서 이 PART 전체를 `CLAUDE.md`로 복사한다. AI는 매 세션 시작 시 이 PART와 현재 작업 단계(PART 16)를 읽는다. **어기면 CI가 실패하도록 `tools/check.sh`에 린트를 넣는다.**

## 3.1 주석 금지 (최우선)

1. **주석을 쓰지 않는다.** `#` 주석, `##` 문서 주석, 코드 블록 주석 모두 금지. GDScript/Go/Python/셸/JSON 전부 해당. (JSON은 원래 주석이 없다.)
2. 설명이 필요하면 **이름을 고치거나 함수를 쪼갠다.** 의도는 함수명/변수명/상수명으로 드러낸다.
3. 예외: 셸 스크립트 첫 줄 shebang, Go 빌드 태그/`//go:generate`/`//go:embed` 지시자, GDScript 어노테이션(`@export`, `@warning_ignore`)은 주석이 아니므로 허용.
4. 문자열 안의 `#`(색상 코드 `"#FF5A1F"` 등)은 주석이 아니다. 린트는 문자열 리터럴을 건너뛰고 검사한다.
5. 미완성 표시(TODO/FIXME) 금지. 후속 작업은 `docs/BACKLOG.md`에 기록한다.
6. 린트: `tools/lint_no_comments.py` — 대상 확장자 `.gd .go .py .sh .tscn .tres`에서 주석 토큰 발견 시 실패. `tools/check.sh`와 CI에서 실행.

## 3.2 언어와 이름

1. 식별자, 로그, 에러 메시지, 커밋 메시지: **영어**. 코드에 한글 리터럴 금지. 사용자 노출 문구는 `game/data/i18n/ko.json`, `en.json`의 키로만 참조한다.
2. 파일/폴더/함수/변수: `snake_case`. 클래스(`class_name`): `PascalCase`. 상수: `SCREAMING_SNAKE_CASE`. enum 이름: `PascalCase`, 멤버: `SCREAMING_SNAKE_CASE`. 시그널: 과거형 `snake_case` (`lap_completed`). 불리언: `is_`/`has_`/`can_`/`should_` 접두어. private: `_` 접두어.
3. **물리량 변수에는 단위 접미사를 붙인다**: `_m`, `_mps`, `_kmh`, `_s`, `_ms`, `_hz`, `_kg`, `_n`, `_nm`, `_kw`, `_j`, `_mj`, `_rad`, `_deg`, `_c`(섭씨). 예: `speed_mps`, `brake_force_n`. 접미사 없는 `speed`, `force`, `time` 금지.
4. 약어 금지(`idx`→`index`, `tmp`→의미 있는 이름, `dt`→`delta_s`). 허용 약어: `id`, `ui`, `hud`, `ai`, `rpm`, `elo`.
5. 한 파일에 클래스 하나. 파일명 = `class_name`의 snake_case. 폴더는 PART 5 구조를 따른다.

## 3.3 타입과 구조

1. GDScript는 **모든 변수/매개변수/반환값에 정적 타입을 명시**한다. `project.godot`에서 `untyped_declaration`, `unsafe_property_access`, `unsafe_method_access`, `unsafe_cast`, `unsafe_call_argument`를 **error**로 설정한다. `Variant` 사용 금지(JSON 파싱 경계 제외, 파싱 직후 즉시 타입 객체로 변환).
2. 매직 넘버 금지. 숫자 리터럴은 `0`, `1`, `-1`, `2`, `0.5` 만 허용. 그 외 모든 튜닝 값은 `game/data/*.json` 또는 `game/core/constants/`의 상수 클래스에 둔다.
3. 함수 ≤ 30줄, 파일 ≤ 300줄(하드 상한 400), 매개변수 ≤ 4개(초과 시 타입 객체로 묶는다), 중첩 ≤ 3단계, 순환 복잡도 ≤ 8.
4. 문자열 키 Dictionary로 도메인 데이터를 다루지 않는다. `RefCounted`/`Resource` 타입 클래스를 쓴다. 상태 식별자는 `enum` 또는 `StringName` 상수.
5. 오토로드(싱글톤)는 5개까지: `Log`, `GameData`, `Settings`, `NetSession`, `AudioBus`. 그 외 전역 상태 금지.
6. 신호는 위로, 호출은 아래로(자식은 `signal`로 알리고 부모가 자식 메서드를 호출). 노드 경로 문자열 하드코딩 금지, `@export`/`%UniqueName`/`@onready` 캐시만 사용.
7. 가능한 한 노드는 코드로 조립한다(차량, 트랙, 부품 파츠). 손으로 쓰는 `.tscn`은 루트 씬과 UI 레이아웃에 한정하며 파일당 150줄 이하로 유지한다.

## 3.4 시뮬레이션 코어 규칙 (`game/core`)

1. `core`는 `Node`, `SceneTree`, `Input`, `Time`, `OS`, `DisplayServer`, 렌더링, UI를 **참조하지 않는다.** `RefCounted`와 순수 함수만 쓴다.
2. 결정론: 난수는 `SimRng`(시드 가능, `RandomNumberGenerator` 래퍼)만 사용. `randf()` 직접 호출 금지. 벽시계 시간 사용 금지. 시뮬레이션 시간은 `tick_index * FIXED_DELTA_S`로만 계산한다.
3. `_physics_process`는 `Simulation.step()`만 호출한다. 고정 스텝 1/120 s. 가변 delta 사용 금지.
4. 시뮬레이션 코드에서 `await`, `Timer`, `call_deferred` 금지.
5. 틱당 힙 할당 금지: 배열/객체는 생성자에서 한 번 만들고 재사용한다. 수치 배열은 `PackedFloat64Array`/`PackedInt32Array`. 문자열 연결/`str()`/`format()`을 틱 경로에서 호출하지 않는다.
6. 모든 물리 상태는 `VehicleState`(직렬화 가능, `copy_from()`/`equals_within()` 제공)에 담는다. 클라이언트 예측/되감기는 이 객체 복사로 구현한다.
7. 불변식은 `assert`로 명시한다(NaN/Inf 금지, 정규화 범위). 릴리스 빌드에서도 서버는 NaN 감지 시 해당 차량을 격리하고 로그를 남긴다.

## 3.5 서버 권위 / 네트워크 규칙

1. 클라이언트는 **입력만** 보낸다. 위치/속도/랩/순위/충돌/ELO를 결정하지 않는다.
2. RPC/메시지 함수 접두어: 클라→서버 `c2s_`, 서버→클라 `s2c_`. 서버 핸들러의 첫 줄은 **검증**(발신자, 상태 머신 단계, 값 범위, 빈도 제한)이다. 실패 시 로그 + 무시.
3. 네트워크 메시지 포맷은 `game/net/messages/`의 타입 클래스에서만 정의한다. 필드 추가 시 프로토콜 버전을 올린다.
4. 모든 시간은 서버 틱 번호 기준.

## 3.6 에러 처리 / 로깅

1. 실패 가능한 연산은 `Result`(ok/err 값 객체)로 반환한다. 에러를 삼키지 않는다. `push_error`/`print` 직접 호출 금지, `Log.info|warn|error(tag, message, fields)`만 사용.
2. Go: 에러는 반환하고 `fmt.Errorf("context: %w", err)`로 감싼다. `panic` 금지(초기화 실패 제외). 로깅은 표준 `log/slog` 구조화 로그.
3. 외부 입력(네트워크, 파일, JSON)은 항상 검증 후 사용한다. JSON 데이터 파일은 `tools/validate_data.py`가 스키마 검증한다.

## 3.7 성능 규칙

1. `_process`/`_physics_process` 안에서 `get_node`, `find_child`, 그룹 조회 금지.
2. 서버는 8대 시뮬레이션이 틱당 1.5 ms를 넘지 않아야 한다(PART 15 계측).
3. 선제적 최적화 금지. 프로파일로 병목이 증명된 곳만 최적화한다. 증명 없이 GDExtension 도입 금지.

## 3.8 테스트 규칙

1. 순수 로직(물리 수식, ELO, 스탯 집계, 매칭, 데이터 파서)은 모두 GUT 단위 테스트(Go는 `testing`)를 가진다. 커버리지 목표: `game/core` 라인 80% 이상, `backend` 70% 이상.
2. 버그 수정은 먼저 실패하는 회귀 테스트를 추가한 뒤 고친다.
3. 물리/타이어/세팅 수치를 바꾸면 **랩타임 회귀 테스트**(§15.2)를 반드시 실행하고 결과를 커밋 메시지 본문에 기록한다.
4. "됐습니다"라고 보고하기 전에 `tools/check.sh`를 실행한다. 실패한 테스트/스킵한 단계를 숨기지 않는다.

## 3.9 Git 규칙

1. **모든 코딩 작업은 작업 후 커밋한다.** 하나의 논리적 변경 = 하나의 커밋. 모든 커밋은 `tools/check.sh`를 통과해야 한다.
2. 커밋 메시지는 영어 Conventional Commits: `feat(core): add tyre thermal model`. 타입: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `data`.
3. 지정된 작업 브랜치에만 푸시한다. 타인 브랜치 이력 재작성 금지. 비밀값(키, 토큰, DB 암호)과 `.godot/`, 빌드 산출물 커밋 금지.
4. 한 세션 = 한 단계(PART 16의 작업 번호 하나). 여러 단계를 섞지 않는다.

## 3.10 의존성 / 보안 / 파일 형식

1. 서드파티: Godot는 GUT만. Go는 표준 라이브러리 + `pgx/v5`, `go-redis/v9`, `golang-jwt/jwt/v5`, `golang.org/x/crypto`(argon2id) 만 허용. 추가 시 이 문서의 허용 목록을 먼저 갱신한다.
2. `eval`, `OS.execute`, `OS.shell_open`(UI 외부 링크 제외), 동적 스크립트 로드 금지. SQL은 파라미터 바인딩만 사용한다.
3. 인코딩 UTF-8, 줄바꿈 LF, 파일 끝 개행 1개. GDScript/Go는 탭 들여쓰기, JSON/YAML/Python은 스페이스(JSON 2칸, Python 4칸). `.editorconfig`로 강제한다.
4. 에셋은 CC0/OFL/Apache-2.0만. 출처를 `docs/ASSET_CREDITS.md`에 기록.

## 3.11 AI 작업 방식

1. 세션 시작: 이 문서의 PART 3과 해당 작업 번호를 읽는다. 모르거나 모호한 점은 **추측하지 않고 질문**한다.
2. 범위 엄수: 작업 번호에 적힌 것만 만든다. 문서에 없는 기능, 추가 추상화, 미래 대비 코드를 넣지 않는다.
3. 수용 기준(§16 각 작업의 "완료 조건")을 만족하는 테스트가 통과해야 완료다.
4. 답변은 핵심만 간결하게 보고한다. 실패/주의점은 반드시 알린다.

# PART 4. 기술 스택

## 4.1 엔진: Godot 4.4 + GDScript

바이브 코딩에서 엔진 선택 기준은 하나다. **AI가 텍스트만으로 게임 전체를 만들 수 있는가.**

| 항목 | Godot 4 | Unity | Unreal 5 |
|---|---|---|---|
| 씬 포맷 | `.tscn` 텍스트 | YAML + GUID 지옥 | `.umap` 바이너리 |
| 리소스 | `.tres` 텍스트 | `.mat` + meta 쌍 | 바이너리 |
| AI의 씬 직접 생성 | 가능 | GUID 관리 필요, 깨지기 쉬움 | 사실상 불가 |
| 컴파일 | 불필요 | C# 필요 | C++ / Blueprint(바이너리) |
| 헤드리스 | `--headless` 기본 | 복잡 | 무거움 |
| 전용 서버 | 공식 headless export | 별도 | 무거움 |

- 버전: **Godot 4.4.x 안정판 고정**. 업그레이드는 별도 작업 번호로만 한다.
- GDScript 선택 이유: 컴파일 단계가 없어 수정→실행 루프가 1초 이내. 병목이 측정되면 그 부분만 GDExtension으로 교체(3.7).
- GDScript의 `float`은 64비트 배정밀도다. 시뮬레이션은 전부 이 정밀도로 수행한다.
- **Jolt/`RigidBody3D`/`VehicleBody3D`는 차량 시뮬레이션에 사용하지 않는다** (결정 D1). 렌더링용 `Node3D`와 레이캐스트 없는 순수 수학으로 시뮬레이션한다.

## 4.2 아키텍처 핵심: 시뮬레이션 코어와 프레젠테이션의 분리

```
        ┌───────────────────────── game/core (순수 시뮬, 노드 없음) ─────────────────────────┐
입력 ─▶ │ InputFrame ─▶ Simulation.step(dt=1/120) ─▶ VehicleState[8], RaceState              │
        └───────────────────────────────────────────────────────────────────────────────────┘
              ▲ 같은 코드                                   ▲ 같은 코드
   [클라이언트: 예측 + 재조정 + 렌더]                [헤드리스 서버: 권위 시뮬 + 판정]
```

- 동일 `core` 코드가 클라이언트(예측)와 서버(권위)에서 실행된다. 물리 불일치가 구조적으로 발생하지 않는다.
- 렌더링 계층은 `VehicleState`를 읽어 `Node3D` 변환/휠 회전/이펙트로 표시만 한다.
- 지면 조회는 레이캐스트가 아니라 **트랙 해석 조회**(`TrackQuery`): 위치(x,z) → 중심선 거리, 횡 오프셋, 노면 종류, 높이, 경사, 뱅크, 벽까지 거리. 트랙이 스플라인에서 절차 생성되기 때문에 가능하다.

## 4.3 네트워크

- 전송: Godot 내장 **ENet(UDP)**. 서버는 Godot 헤드리스 프로세스 1개 = 룸 1개.
- 서버 권위 + 클라이언트 예측 + 서버 재조정 + 원격 차량 스냅샷 보간 (상세 PART 10).

## 4.4 백엔드

- **Go 1.22+** 단일 모듈, 서비스: `auth`, `matchmaking`, `rating`, `profile`, `inventory`, `shop`, `mission`, `social` (모놀리스 1바이너리, 내부 패키지로 분리).
- **PostgreSQL 16** (영속), **Redis 7** (매칭 큐, 세션, 레이트리밋).
- 전송: HTTPS REST(JSON) + WebSocket(큐 이벤트/매치 배정 푸시).

## 4.5 배포

- Docker. 게임 서버는 리전별 인스턴스: `kr`(서울), `us-east`, `eu-west`.
- 서버 인스턴스 용량 가정: 4 vCPU 1대 = 룸 12개 (룸당 CPU 25% 이하 목표).
- CI: GitHub Actions — `tools/check.sh` (린트 + 데이터 검증 + GUT + Go 테스트 + 랩타임 회귀).

## 4.6 최종 스택 요약

```
클라이언트     Godot 4.4 / GDScript (자체 2.5D 차량 솔버)
게임 서버      Godot 4.4 헤드리스 (동일 core 코드, 서버 권위)
백엔드         Go + PostgreSQL + Redis
전송           ENet(UDP, 게임) / HTTPS+WebSocket(메타)
배포           Docker, 게임서버 리전별 인스턴스
검증           GUT + 헤드리스 AI 드라이버 랩타임 회귀 + 파라미터 스윕 + 데이터 스키마 검증
```

모든 수치는 **[초기값]**이며 Phase 1.8 / 3.2 / 3.9에서 튜닝한다. 튜닝 시 이 PART의 표를 갱신한다. 단위는 SI(m, kg, s, N, W, J)이며 화면 표시만 km/h를 쓴다.

## 6.1 시간/좌표

## 6.6 공기역학

- 항력 `F_drag = 0.5·ρ·CdA·v²`, 다운포스 `F_df = 0.5·ρ·ClA·v²`.
- `CdA = 0.95 + 0.009·DRG` m², `ClA = 2.0 + 0.035·DWF` m² (스탯 DRG, DWF는 §7.3 최종 스탯).
- 다운포스 전후 배분 `front_share = clamp(0.42 + 0.004·(FW_slider − RW_slider), 0.30, 0.55)`.
- 손상 보정: 프론트 윙/리어 윙/차체 체력에 따른 다운포스·항력 변화는 §6.12.
- **슬립스트림** (앞차 뒤 주행):
  - 조건: 앞차 속도 ≥ 40 m/s, 앞차 후방 거리 `d` ∈ [2, 60] m, 횡 오프셋 `|y|` < 1.6 m.
  - `f_d = 1 (d ≤ 8 m)`, 이후 60 m까지 선형 감소. `f_y = 1 − |y|/1.6`.
  - 목표 계수 `s_target = 0.18 · f_d · f_y`, 실제 계수는 상승 시정수 0.6 s, 하강 시정수 0.4 s로 추종.
  - 효과: `CdA_effective = CdA · (1 − s)`. (CdA 1.40 기준 직선 최고속도 약 +20 km/h)
- **더티 에어**: 앞차 후방 `d ≤ 30 m`, `|y| < 1.6 m`일 때 `ClA_effective = ClA · (1 − 0.20·f_d30·f_y)` (최대 −20%). 코너에서 바짝 붙으면 그립이 줄어 추월은 코너 탈출 속도와 슬립스트림이 만든다.
- 속도 의존 각도 변화/지면 효과는 모델링하지 않는다.

## 6.7 타이어

**Pacejka Magic Formula 간이형** `F = D·sin(C·atan(B·x − E·(B·x − atan(B·x))))`

| 축 | B | C | E | 입력 x |
|---|---|---|---|---|
| 횡 (lateral) | 10.0 | 1.90 | 0.97 | 슬립각 α [rad] |
| 종 (longitudinal) | 12.0 | 1.65 | 0.30 | 슬립비 κ |

- `D = μ · Fz`, `μ = μ_peak · load_sens(Fz) · surface_mult · temp_mult · wear_mult`.
- `μ_peak = 1.70 + 0.0070·COR` (COR 50 → 2.05).
- 하중 민감도 `load_sens = max(0.6, 1 − 2.0e-5 · (Fz − 3000))`.
- 슬립각 `α = atan(v_lat / max(|v_long|, 1.0))`, 슬립비 `κ = (ω·r − v_x)/max(|v_x|, 1.0)`.
- 복합 슬립: 마찰 타원 — 종/횡 힘을 `√((Fx/Fx_max)² + (Fy/Fy_max)²) ≤ 1` 로 정규화.
- 과도 응답(이완 길이): 횡 0.35 m, 종 0.25 m. `dF/dt = (v/σ)(F_ss − F)`.
- 후륜 횡그립 편향 `rear_bias = 0.98 + 0.0008·STB` (STB가 높을수록 오버스티어 억제).
- 요 감쇠 `yaw_damping = 600 + 18·STB` N·m·s.

## 6.8 브레이크

- 최대 제동력 `F_brake_max = 36,000 + 280·BRK` N (BRK 50 → 50 kN). 실제 제동력은 타이어 종력 한계로 제한된다.
- 전후 제동 배분 `front_bias = 0.46 + 0.0020·BB_slider` (BB 50 → 56%). 이상 배분 `f* = 0.56 + 0.0008·(DWF − 50)`. 효율 `eff = clamp(1 − 2.0·|front_bias − f*|, 0.70, 1.00)`. 앞이 과하면 앞 락업(언더스티어/마모), 뒤가 과하면 불안정(`STB` 감소 효과).
- **ABS 보조(켰을 때)**: 휠 락업 방지, 대가로 제동력 −2%.
- 브레이크 온도 `T_b`: 제동 시 상승, 주행풍으로 냉각. 페이드 `1 − 0.40·clamp((T_b − 750)/250, 0, 1)`.
- 브레이크 마모 `w_b`: 제동 에너지(J) 누적, `E_life = 300 MJ`(BWR 50 기준)에서 1.0, 배수 `exp(0.022·(BWR−50))`. 제동력 배수 `1 − 0.30·w_b²`.

## 6.9 에너지 시스템

- 배터리 용량 4.0 MJ (고정). 레이스 시작 50%, 퀄리 시작 100%.
- **충전**: 제동 회수 `E_regen = η · ΔKE_brake`(η = `0.20 + 0.006·ECH`, ECH 50 → 0.50). 스로틀 10% 미만 코스팅 시 `40 kW · (η/0.5)` 회수.
- **배치**: 버튼 누르는 동안 추가 구동 출력 `70 + 1.4·EOU` kW(EOU 50 → 140 kW) 가산. 배터리 0 이면 불가.
- 효과: 가속 증가, 최고속도 증가 (기준차 318 → 339 km/h), 추월 능력 증가. 지속 가능 시간 = 4 MJ / 140 kW ≈ 28.6 s (전량 사용 시).
- 전략: 마지막 랩에 저장해 몰아 쓰기, 매 랩 직선에서 사용 등은 플레이어 선택. **자동 배치 보조(Auto Deploy)**: 직선 풀스로틀 구간에서 자동 배치 (초보 프리셋 기본 ON).

## 6.11 차량 간 충돌

- 2D OBB(5.50×2.00 m) SAT 검출, 임펄스 해결. 반발계수 0.15, 마찰 0.30, 질량 동일.
- 벽: 트랙 경계 폴리라인(코스 가장자리 + 런오프 폭) 대비 부호거리, 임펄스 반발 0.15, 마찰 0.25.
- 접촉 해결 후 겹침 분리는 위치 보정으로 처리하고 에너지는 증가하지 않는다.
- **핑 공정 충돌**: 접촉한 두 차량 중 하나라도 RTT > 120 ms면 해당 접촉의 임펄스 ×0.6, 손상 ×0.5. (PART 10)
- **고스트 상태**: 퀄리파잉 전원, 피트레인 전원, 리셋/역주행 경고 후 고스트 차량은 충돌 판정에서 제외.
- **Start Protection**: 출발 신호 후 12초간 (또는 첫 코너 통과 시까지 중 먼저 끝나는 쪽) 충돌 손상 ×0.3, 차량 간 임펄스 ×0.5. 완전 무적 아님.

## 6.12 손상 모델

**존(Zone) 8개, 체력 0~100**: 프론트 윙(FW), 리어 윙(RW), 서스펜션 FL/FR/RL/RR(4), 엔진(EN), 차체(BD). 타이어/브레이크는 §6.7/§6.8의 마모·펑크로 별도 관리한다.

**충돌 손상량** (벽 또는 차량):
- 충격 에너지 `E = 0.5·m_eff·v_n²` (벽: m_eff = 800 kg, 차량-차량: 400 kg).
- 임계 에너지 `E0 = 3,600 J`(v_n ≈ 3 m/s 이하는 무손상). 기준 에너지 `E_ref = 160,000 J`(v_n = 20 m/s ≈ 72 km/h).
- 총 손상 `D = 100 · (E − E0)/E_ref · dmg_mult`, `dmg_mult = 1.4 − 0.008·STB` (STB = 차량 안정성 스탯. 안정성이 높을수록 손상 감소).
- 접촉점별 분배(합 100%):

| 충격 위치 | FW | RW | 서스펜션 | EN | BD |
|---|---|---|---|---|---|
| 정면 | 50% | 0 | 전륜 서스 각 10% (합 20) | 10% | 20% |
| 후면 | 0 | 50% | 후륜 서스 각 10% (합 20) | 15% | 15% |
| 좌측/우측 면 | 15% | 15% | 해당 측 서스 각 20% (합 40) | 5% | 25% |

**손상 단계 (존 체력 기준)**:

| 단계 | 존 체력 | 효과 |
|---|---|---|
| 정상 | 90~100 | 없음 |
| 경미 | 60~89 | 성능 소폭 감소 |
| 중간 | 30~59 | 조향 불안정, 속도 감소, 코너링 감소 |
| 심각 | 0~29 | 성능 크게 감소, 리타이어 가능 |

**존별 효과 (체력 h, 손상 비율 d = 1 − h/100)**:

| 존 | 효과 |
|---|---|
| FW | 전방 다운포스 `×(1 − 0.45·d)`, 중간 이하에서 `COR −10·d`; 체력 0 이면 윙 탈락(전방 다운포스 0, 항력 −8%) |
| RW | 후방 다운포스 `×(1 − 0.45·d)`, `STB −10·d`; 0 이면 탈락 |
| 서스펜션(각 휠) | 해당 휠 토 오프셋 `1.5°·d`(차량이 한쪽으로 끌림), 접지 `×(1 − 0.2·d)`; 한 축 양쪽 모두 0 이면 이동 불가 |
| EN | 출력 `×(0.7 + 0.3·h/100)`; 0 이면 DNF |
| BD | 항력 `×(1 + 0.15·d)`, 바닥 다운포스 `×(1 − 0.10·d)`; 충돌 손상 배수 `×(1 + 0.3·d)` |

**DNF(리타이어) 조건 (하나라도)**: 엔진 체력 0 / 한 축 서스펜션 양쪽 0 / 총 체력 합(8존 합계, 최대 800) < 150 이고 속도 < 40 km/h 20초 지속 / 리셋 횟수 초과(§9.9) / 역주행 강제 퇴장 / 접속 이탈.

**피트 수리 (§9.6)**: FW, RW, 서스 4개, BD는 복구 가능, EN은 복구 불가(영구). 펑크/마모 타이어는 교체.

## 6.13 랩 타이밍

- 체크포인트 100 m 간격(중심선 거리 기준), 순서대로 통과해야 유효. 건너뛰면 해당 랩은 무효(퀄리) / 순위에서 해당 구간 재통과 필요(레이스).
- 섹터 3개(트랙 DSL의 `sectors` 분할). 랩타임 해상도 1 ms.
- 진행도 `progress_m` = 중심선 투영 거리(랩 수 × 트랙 길이 + 현재 위치). 순위 = 진행도 내림차순, 동률은 마지막 체크포인트 통과 시각.
- 앞뒤 차 갭(초) = 뒤 차가 앞 차의 현재 지점을 지난 시각 차이(서버가 중심선 100 m 샘플별 통과 시각 기록).

## 6.14 레이싱 라인 / 속도 프로파일

- 생성: 트랙 중심선을 5 m 간격으로 샘플링, 코스 폭 − 2.0 m 마진 내에서 곡률 합 최소화(반복 완화)로 라인 산출.
- 속도 프로파일: 점질량 준정상 모델 — 각 점 `v_lat = sqrt(μ·g / (κ − μ·k_df))` (κ ≥ μ·k_df 일 때, `k_df = 0.5·ρ·ClA/m`), 아니면 출력 한계 속도. 앞→뒤 제동 패스(`a_brake = μ(g + k_df v²)·0.95 + 항력`), 뒤→앞 가속 패스.
- 용도: AI 드라이버 기준선, 레이싱 라인 가이드, 패배 분석 기준, Engineer 트랙 메트릭, 트랙 기준 랩타임.
- **트랙 기준 랩타임** = 속도 프로파일 합 × 1.03 (인간 주행 마진).

## 6.15 AI 드라이버

- 목적: 검증 인프라, 튜토리얼/일반전 상대, 패배 분석 기준.
- 라인 추종(전방 주시 거리 `max(12 m, 0.5·v_mps)`), 속도 프로파일 추종, 입력은 플레이어와 동일한 `InputFrame`.
- 스킬 5단계: 속도 프로파일 배율 `[0.88, 0.92, 0.95, 0.98, 1.00]`, 공격성(추월 시도 임계 갭) `[0.3, 0.4, 0.5, 0.6, 0.7] s`, 실수 확률은 SimRng 시드 기반 결정적(제동 지점 오차 ±`[12, 8, 5, 3, 1]` m).
- 경쟁전에서는 사용하지 않는다(D14).

## 7.3 스탯 집계 공식

```
stat[i] = clamp( 50
               + Σ_slots   spread(rarity[slot]) · archetype_delta[slot][i]
               + Σ_sliders slider_coeff[slider][i] · (slider_value − 50)
               + Σ_modes   mode_delta[mode][i]
               + trait_stat_effects[i],
                0, 100 )
```

- 각 슬롯의 `B`(Balanced) 아키타입은 델타가 전부 0 → 기준차(전부 B, 슬라이더 50, 모드 Standard)는 모든 스탯 50.
- **무료 점심 금지 규칙**: 모든 아키타입/슬라이더/모드의 델타는 `Σ(▲ 델타) − Σ(▼ 델타) = 0`을 만족한다(▼ 스탯 증가는 불이익으로 계산). `tools/validate_data.py`가 검사한다.
- 최종 스탯 → 물리 파라미터 변환은 §7.2의 식. 변환 후 성능 요약(Garage 표시)은 시뮬레이터 공식으로 계산한다(§7.11).

- 총 스탯 합은 모든 등급에서 동일(항상 0 합). 높은 등급은 **특화 정도, 세팅 범위, 모드, 특성**을 늘릴 뿐 총합을 올리지 않는다 (D11).
- 목표: "Legendary를 가지고 있으면 무조건 이긴다"가 아니라 **"Legendary를 어떻게 세팅하느냐가 중요하다."**
- **[목표]** 같은 세팅 의도에서 Legendary 풀세트와 Common 풀세트의 최적 랩타임 차이 ≤ 0.8% (트랙 6종 평균). 초과하면 spread/W/특성 강도를 낮춘다. 또한 Legendary가 Common보다 느린 트랙/세팅 조합이 **최소 1개 이상** 존재해야 한다(오히려 불리한 특화 선택 가능).
- 강화는 아키타입 단위로 누적된다: Common → Rare 100 → Epic 300 → Legendary 900 (아키타입당 총 1,300 스크랩). 27종 전부 Legendary = 35,100 스크랩.

## 7.6 특성(Trait) 규칙

- 아키타입당 정확히 1개. Rare 이상에서 활성, 강도는 등급 배율(§7.5)을 곱한다.
- 모든 특성은 이점과 대가를 가진다. 수치는 표의 "Rare 기준"이며 Epic은 ×1.25, Legendary는 ×1.5(대가도 같은 배율).
- 특성 효과는 `TraitEffects`가 물리 파라미터에 직접 곱/가산으로 적용한다(스탯 합에는 넣지 않는다).

## 7.7 고급 세팅 슬라이더 5종 / 모드 4종

**슬라이더**: 값 0~100, 기본 50. 해당 슬롯 부품의 등급이 허용 범위(§7.5)를 정하고, 범위 밖은 비활성. `+1`(50 초과 1단위)당 스탯 변화:

| 슬라이더 | 연결 슬롯 | 스탯 계수 (+1당) | 합 |
|---|---|---|---|
| Front Wing | FW | DWF +0.30, DRG +0.18, COR +0.06, STB −0.18 | 0 |
| Rear Wing | RW | DWF +0.35, DRG +0.20, TOP −0.10, STB −0.05 | 0 |
| Gear Ratio (높을수록 가속형) | GB | ACC +0.30, TOP −0.30 | 0 |
| Suspension (높을수록 단단) | SU | COR +0.20, ACC +0.05, STB −0.20, TWR +0.05 | 0 |
| Brake Balance (전륜 편향) | BR | 스탯 변화 없음. 물리 `front_bias = 0.46 + 0.0020·BB` (§6.8) | — |

**모드 스위치**: 3단(방어/Standard/공격). 방어 모드는 Rare, 공격 모드는 Epic 이상에서 개방. 연결 슬롯의 등급이 기준.

| 모드 | 연결 슬롯 | 방어 | Standard | 공격 |
|---|---|---|---|---|
| 엔진 모드 | EN | Eco: TOP −8, EDU +8 | 없음 | Push: TOP +8, EDU −8 |
| 에너지 모드 | ES | Harvest: ECH +12, EOU −12 | 없음 | Attack: ECH −12, EOU +12 |
| 라이드 하이트 | CH | High: DWF −4, STB +4 | 없음 | Low: DWF +4, STB −4 (연석 접촉 시 그립 −8%) |
| 타이어 공기압 | TY | High: COR −6, TWR −6 | 없음 | Low: COR +6, TWR +6 |

## 7.13 밸런스 수용 기준 (자동 스윕, Phase 3.9)

3. 트랙 A 최적 세팅을 트랙 B(다른 유형)에 적용하면 B 최적 대비 +1.0% 이상 느려야 한다.

5. 프리셋 5종 모두 최소 1개 트랙에서 5개 중 1위여야 한다.
6. 타이어: 트랙별로 0스톱/1스톱/2스톱 전략의 총 레이스 시간 차가 ±3% 이내 (전략이 균형).
7. 위반 시 계수(§7.2), 아키타입 델타, 타이어 수명을 조정하고 이 문서를 갱신한다.

- 세그먼트 종류:
  - `straight {length_m, flex?}`
  - `corner {angle_deg(+좌/−우), radius_m, banking_deg?, elevation_m?, width_m?}`
  - `chicane {width_m, length_m}` (순 방향 변화 0, 횡 이동 `width_m`)

| 검증 | 기준 |
|---|---|
| 코스 폭 | 10~18 m |
| 최소 코너 반경 | ≥ 30 m |
| 세그먼트 수 | 8~30 |
| 폐합 오차 | < 0.5 m |
| 비인접 구간 중심선 간격 | ≥ 40 m (자기 교차 금지, 교차로 없음) |
| 최대 경사 | ≤ 12 % |
| 최대 뱅킹 | ≤ 12° |
| 크레스트 수직 곡률 | 해당 지점 프로파일 속도에서 하중 ≥ 정적의 20 % |
| 기준 랩타임 | 5개 서킷 유형별 목표 범위 내 |
| 피트레인 | 메인 스트레이트에 위치, 길이 360~420 m, 박스 8개 |

## 8.3 트랙 컴파일러 산출물

JSON → `TrackData`(순수 데이터) + `TrackMeshBuilder`(렌더 메시):

1. 중심선 샘플링: 2 m 간격 `Curve3D`/배열 (위치, 접선, 곡률, 높이, 뱅킹, 폭).
2. 노면: 폭 방향 메시 스트립 + 러버 라인 텍스처 파라미터.
3. 연석: 코너 안쪽, 아펙스 ±15 m, 폭 1.2 m. 돌출 연석은 시케인/헤어핀 안쪽만.
4. 런오프: 코스 가장자리 바깥으로 폭 `runoff.width_m`(기본 8 m: 아스팔트 4 m + 잔디/자갈 4 m), 그 바깥에 배리어(`tyre_wall` 또는 `concrete` 또는 `armco`). 시가지(T02)는 런오프 1.5 m + 콘크리트 벽.
5. 충돌 폴리라인: 좌/우 배리어 경계.
6. 체크포인트: 100 m 간격. 섹터 경계.
7. 레이싱 라인 + 속도 프로파일(§6.14) + 기준 랩타임.
8. 피트레인: 코스 바깥쪽 22 m, 폭 12 m, 피트 진입/출구 연결로, 박스 8개(그리드 순서와 일치).
9. 스타트 그리드: 시작선 뒤로 8 m 간격 2열 지그재그 (홀수 순번 −2.5 m, 짝수 +2.5 m).
10. `profile`(Engineer 입력): `length_m`, `longest_straight_m`, `full_throttle_share`, `slow_corner_count`(apex < 100 km/h), `corner_count`, `lateral_g_share`(횡G > 3G 비율), `elevation_range_m`, `braking_zone_count`, `ref_lap_s`.
11. `engineer`: `compound`, `strategy` (오프라인 스윕 결과 삽입, `tools/param_sweep.gd`).
12. 장식: `MultiMeshInstance3D`로 관중석/광고판/건물을 스플라인 따라 `scenery_seed`로 배치.

## 8.4 피트레인 / 피트 시간

- 피트 진입 구간부터 출구까지 속도 제한 80 km/h (자동 리미터), 충돌 없음(고스트).
- 피트 손실 시간 `pit_loss_s = pit_length/22.2 − pit_length/v_avg_lap + stationary_s`. **[목표]** 정차 제외 순수 피트레인 손실 11~14 s.

## 8.5 트랙 로테이션

- 매칭 완료 시 서버가 시드 기반으로 선택. 풀 6개. 해당 리전 큐의 **최근 3개 트랙은 제외**, 참가자 중 누구의 직전 트랙과도 겹치지 않도록 가능한 한 회피(불가능하면 허용). 가중치는 균등.
- 트랙이 추가되면 풀에 포함, 신규 트랙은 첫 주 가중치 ×2.

## 8.6 영감 소스 정책

실제 서킷의 특징(긴 스트레이트+헤어핀, 시가지 좁은 벽, 고저차 등)만 참고한다. 실존 서킷의 레이아웃/이름/코너명을 그대로 복제하지 않는다.

## 9.2 매칭 (§12, §13)

**기준**: ELO, 핑, 대기 시간, 지역.

| 최장 대기 | ELO 허용 범위 (±) |
|---|---|
| 0 s | 100 |
| 10 s | 150 |
| 20 s | 250 |
| 30 s | 400 |
| 45 s | 600 |
| 60 s 이상 | 1000 |

- 값은 서버 설정(`matchmaking.json`)이며 데이터로 조정한다. 목표는 실력 차이와 대기시간의 균형.
- 매치 구성: 가장 오래 기다린 플레이어를 앵커로 잡고, 앵커의 현재 ELO 범위 안에서 같은 리전 후보를 모은다. **8인**이 모이면 즉시 시작. 앵커 대기 30 s 이상이면 **6~7인으로도 시작**.
- 지역/핑: 클라이언트가 3개 리전(kr, us-east, eu-west)에 핑을 측정해 보고. 매치 서버 리전은 후보 전원의 **최대 RTT가 최소인 리전**. 후보 중 해당 리전 RTT > 150 ms인 플레이어는 제외(소프트 선호 ≤ 100 ms).
- 큐 틱 1초. 한 플레이어는 동시에 한 큐에만 존재.
- 솔로 큐 전용(D13).
- 레디체크 미수락 3회/1시간 → 5분 큐 제한.

## 9.3 ELO 계산 (§5, §6)

멀티플레이어 확장 Elo (순위 기반 페어와이즈). 순위별 고정 점수를 지급하지 않는다.

```
E_ij = 1 / (1 + 10 ^ ((R_j − R_i) / 400))
S_ij = 1 (i가 j보다 높은 순위) / 0.5 (동률) / 0
ΔR_i = K_i / (N − 1) · Σ_{j≠i} (S_ij − E_ij)
```

| 항목 | 값 [초기값] |
|---|---|
| 초기 ELO | 1000 |
| K (배치 경기, 첫 10경기) | 64 |
| K (일반) | 40 |
| K (ELO ≥ 2000) | 32 |
| 최소 ELO | 0 |
| 이탈 추가 페널티 | −20 (§9.12) |
| 반올림 | 정수로 반올림, 최소 변동 ±0 (참가만으로 +ELO 없음) |

- 동일 K 플레이어만 있는 경우 변동 합은 정확히 0(제로섬). `EloCalculator` 테스트로 보장한다.
- 순위 판정: 완주자는 (랩 수 내림차순, 기록 오름차순) → DNF(진행도 내림차순) → 이탈자(이탈 시각이 빠를수록 하위).
- 검증 예시(K=40, 상대 전원 평균 가정):

| 내 ELO | 상대 | 순위 | ΔELO |
|---|---|---|---|
| 1400 | 1500 | 1위 | +25.6 (큰 폭 상승) |
| 1400 | 1500 | 4위 | +8.5 (소폭 상승) |
| 1400 | 1500 | 8위 | −14.4 |
| 1600 | 1400 | 1위 | +9.6 (소폭 상승) |
| 1600 | 1400 | 8위 | −30.4 (큰 폭 하락) |
| 1200 | 1200 | 1위 | +20.0 |

- 결과 화면: `ELO 1428 → 1451 (+23)` 및 변화 이유 상위 3개 (예: "ELO 1620 상대를 이김 +9").
- 승부 조작 방지: 같은 두 플레이어가 24시간 내 3회 초과 같은 매치에 배정되면 해당 쌍에서 얻는 이득을 ×0.5.
- **[목표]** 100판 시뮬레이션(실력 분포 고정 8인 풀)에서 최종 ELO와 실력의 스피어만 상관 ≥ 0.85, 평균 ELO 드리프트 ≤ ±10/1000판.

## 9.5 퀄리파잉 (§37~40)

- 방식: **롤링 스타트 1랩 타임어택**. 피트 출구에서 80 km/h로 출발선을 통과하는 순간 타이머 시작, 다음 통과 시 종료. 최대 **2회 시도**, 베스트 랩 채택.
- 참가자 전원 동시 진행, 서로 **고스트**(충돌 없음, 반투명 표시). 서버가 기록을 집계해 순위를 비교한다(§91 `Player → 1 Lap → Time → Server → Ranking`).
- 시도 중단: 코스 이탈로 체크포인트 누락 시 해당 시도 무효. 시도 후 `RESTART` 버튼으로 2번째 시도 (피트 출구로 즉시 복귀, 창 시간은 계속 흐름).
- 타이어: 새 타이어(시작 온도 최적의 90%), 에너지 배터리 100%.
- 창 종료 시 진행 중인 시도는 완료까지 허용(최대 +2 s ref_lap 초과 시 무효). 기록 없는 플레이어는 최하위 그리드.
- 그리드: 베스트 랩 오름차순, 동률은 먼저 기록한 순서. 기록 무효자는 뒤쪽 배치(입장 순).
- UI(§40): `QUALIFYING / P1 PlayerA 1:28.421 / P2 YOU 1:28.592 ...` — 현재 순위, 섹터 기록(보라=전체 베스트, 초록=개인 베스트, 노랑=느림), 베스트 랩, 폴 포지션 예상.

## 9.6 피트스톱 (§44~46)

- **요청**: PIT 토글. 피트 진입선을 지나기 전에 요청되어 있어야 이번 랩 진입. 피트 계획 패널에서 다음 컴파운드(S/M/H)와 수리 항목을 사전 지정(미지정 시 같은 컴파운드 + 손상 항목 전체).
- 피트레인: 진입 60 m 전부터 속도 리미터(80 km/h)가 서서히 걸림, 구간 내 충돌 없음(고스트), 추월 허용.
- **정차 시간** (완전 랜덤이 아님 — 결정적 공식):

```
stationary_s = clamp( (2.9 + Σ repair_s) · crew_factor · (1 − chassis_trait) + precision_adj_s , 2.5 , 5.0 )
```

| 수리 항목 | 추가 시간 |
|---|---|
| 프론트 윙 교체 | +0.8 s |
| 리어 윙 교체 | +0.8 s |
| 서스펜션 복구 (일괄) | +1.2 s |
| 차체 복구 | +1.0 s |
| 브레이크 교체 | +1.2 s |
| 타이어 4본 교체 / 펑크 | 기본 포함 |

| 피트 크루 | crew_factor | 입수 |
|---|---|---|
| Rookie | 1.15 | 기본 |
| Standard | 1.00 | 크레딧 3,000 |
| Pro | 0.92 | 크레딧 9,000 |
| Elite | 0.85 | 크레딧 24,000 |

- 박스 정지 정밀도 `precision_adj_s`: 박스 표식 ±0.3 m = −0.2 s, ±1.0 m = 0, 그 이상 = +0.4 s, 2 m 초과 오버슈트 = +0.8 s.
- 엔진 체력은 수리 불가. 교체된 타이어는 마모 0, 시작 온도 최적의 65%(콜드 타이어 → 3~5초 워밍업).
- 피트 전략 예: 1 Stop Soft → Medium, 2 Stop Soft → Soft → Soft. 트랙/스타일에 따라 달라진다 (§8.1 추천 전략).
- 의무 피트 없음. 한 랩에 피트레인을 지나친 경우(요청 없이) 정상 주행으로 진행.
- 피트레인 진행도는 피트레인 중심선을 본선 진행도에 투영해 계산(순위가 끊기지 않는다).

## 9.7 그랑프리 (§41~43)

상태: `QUALIFYING → GRID → COUNTDOWN → RACE → FINAL LAP → FINISH`.

- 출발: 소등 전까지 모든 차량은 그리드 락(브레이크 홀드)으로 고정 → 조기 출발 불가, 반응은 소등 후 입력 타이밍으로만 결정.
- **Start Protection**: 소등 후 12 s (또는 첫 코너 통과 중 빠른 쪽). 충돌 손상 ×0.3, 차량 간 임펄스 ×0.5. 완전 무적 아님 (§6.11).
- 핵심 시스템: 주행, 추월, 슬립스트림, 에너지, 타이어, 피트, 차량 손상.
- 레이스 길이 목표 5~15분 (출시 트랙 8.4~9.4분).
- 종료: 선두가 마지막 랩을 마치면 체커 플래그. 나머지는 각자 결승선 통과 시 종료. 선두 완주 후 30초가 지나면 남은 차량은 그 시점의 (랩, 진행도)로 분류하고 종료.
- 랩 차이로 뒤처진 차량은 별도 규칙 없음(파란 깃발 없음).
- 레이스 중 세팅 변경 불가(피트의 타이어/수리 제외).

## 9.8 추월 (§49, §50)

슬립스트림(§6.6)이 추월의 핵심. 최고속도, 가속, 코너 탈출, 에너지, 슬립스트림, 주행 라인, 차량 세팅이 영향을 준다. DRS/에너지 존 없음(D6, D7). **[목표]** 8인 레이스당 추월(순위 교환) 8회 이상, 단 한 곳(예: 메인 스트레이트)에서 전체의 60% 이하.

## 9.9 리셋 / 역주행 / 리타이어 (§34, §36)

- **리셋**: R 3초 길게 → 5초 고스트 대기 후 가장 가까운 중심선 지점(정지, 전방 향함)으로 복귀. 타이어/손상 상태 유지. 레이스당 최대 3회, 4번째는 DNF. 퀄리 중 리셋은 해당 시도 무효.
- **자동 정지 감지**: 그리드/피트 외 구간에서 속도 < 5 km/h가 8초 지속되면 리셋 안내 표시.
- **역주행 감지**: 차량 방향과 중심선 접선의 내적 < −0.5이고 속도 > 10 km/h.

| 지속 시간 | 처리 |
|---|---|
| 2 s | 경고 표시 |
| 4 s | 고스트 처리 (충돌 제외) |
| 12 s | 강제 퇴장 (이탈로 취급, §9.12) |

- **리타이어(DNF)**: §6.12 조건 충족 시. DNF 플레이어는 레이스 종료 / 결과 확인 / 관전 중 선택 가능.
- 관전: DNF 또는 종료 후 다른 플레이어 시점 관전(서버가 이미 전송하는 스냅샷으로 카메라만 전환).

## 9.10 운전 스타일과 마모 (§30)

| 스타일 | 지표 | 효과 |
|---|---|---|
| 공격적 | 랩당 슬립 에너지 / 기준 > 1.15 | 랩타임 감소, 타이어 마모↑, 사고 위험↑ |
| 일반 | 0.85~1.15 | — |
| 안정적 | < 0.85 | 랩타임 증가, 마모↓, 안정성↑ |

슬립 에너지 지표는 결과 화면과 패배 분석(§9.15)에 표시.

## 9.11 주행 보조 (§58)

| 보조 | 효과 | 경쟁전 성능 대가 | 초보 프리셋 | 숙련 프리셋 |
|---|---|---|---|---|

## 9.12 이탈 / 탈주 (§66)

| 구분 | 판정 | 처리 |
|---|---|---|
| 고의 이탈 | 메뉴로 나가기, 역주행 강제 퇴장, 연결 끊김 직전 5 s 간 패킷손실 < 30% & RTT < 400 ms | 순위 최하위(이탈 시각 빠를수록 하위) + 추가 −20 ELO, 이탈 카운트 +1 |
| 네트워크 오류 | 연결 끊김 직전 5 s 중 패킷손실 ≥ 30% 또는 RTT ≥ 400 ms | DNF(진행도 순위), 추가 페널티 없음, 네트워크 카운트 +1 (7일 내 5회 이상이면 고의로 취급) |
| 서버 오류 | 서버 크래시/룸 종료 | 매치 무효, ELO 변화 없음 |
| 대량 이탈 | 레이스 2랩 진입 전 4명 이상 이탈 | 매치 무효, 남은 인원 ELO 변화 없음 |

- 재접속 창 30 s: 그동안 차량은 고스트 상태로 70% 페이스 직진 유지. 복귀 시 즉시 제어권 반환. 30 s 초과 시 DNF.
- 이탈 카운트(롤링 24 h) 제한: 2회 경고, 3회 큐 정지 15분, 이후 이탈마다 2배(30, 60, …, 최대 24시간). 7일 무이탈 시 초기화.

## 9.13 ELO 보호 / 악용 방지 (§65)

신규 계정 배치 경기(K=64), 비정상적 반복 탈주 탐지, 고의적 ELO 하락 방지(최하위 반복 + 입력 없음 패턴 → 제재), 파티를 이용한 랭킹 조작 방지(파티 경쟁전 미지원), 승부 조작(§9.3), 비정상 레이스 기록 탐지(§11.5).

## 9.14 라이벌 (§97)

레이스마다 같은 매치 안에서 **ELO 차이가 가장 작은 상대 1명**을 Rival로 지정(동률은 낮은 ELO). 레이스 후 라이벌보다 높은 순위면 크레딧 +10% 및 스크랩 +5 보너스 (소규모). 통계는 프로필에 누적.

## 9.15 패배 분석 (§72)

`WHY DID YOU LOSE?` — 선두(또는 라이벌) 대비 총 시간 차를 항목으로 분해한다. 서버가 매치 중 100 m 구간별 시간/속도/마모/피트를 저장하고, AI 기준선과 비교해 계산:

| 항목 | 산출 |
|---|---|
| Top Speed | 직선 구간(풀스로틀 구간) 시간 차 |
| Cornering | 코너 구간(횡G > 2G) 시간 차 |
| Pit Time | 피트 손실 시간 차 |
| Tyre Degradation | 같은 구간 랩 후반 vs 전반 시간 증가분 차 |
| Driving | 위 항목으로 설명되지 않는 잔차 + 제동 지점/라인 이탈 환산 |

항목 합 = 총 시간 차 (잔차는 Driving). 표시 예: `Top Speed −0.7s / Cornering +0.3s / Pit Time +1.8s / Tyre Degradation +1.1s / Driving +0.9s`. 개선 팁 1줄(i18n 키)을 가장 큰 손실 항목에 대해 표시.

## 9.16 일반전 (§68)

ELO 변화 없음, 자유로운 차량 테스트, 친구와 플레이, 세팅 테스트. 수 인원 1~8(AI 드라이버 스킬 1~5로 빈 자리 채움), 트랙 선택 가능, 날씨 없음, 보상은 경쟁전의 50% (일 20판 한도). 퀄리 건너뛰고 랜덤 그리드 옵션.

## 9.17 친구 / 프로필 / 리플레이 / 관전

- 친구: 추가/삭제/차단, 온라인 상태(Online/In Queue/In Match/Offline), 프로필 열람, 일반전 초대. 최대 친구 수 100. 경쟁전 파티는 후속(D13).
- 프로필 항목(§85): 닉네임, ELO, 티어, 최고 ELO, 우승 횟수, 포디움, 폴 포지션, 베스트랩(트랙별), DNF, 총 레이스, 최근 10경기.
- 리플레이(P2): 서버가 매치 시드 + 차량 세팅 + 전원의 `InputFrame` 스트림을 저장(약 30 KB/매치). 재생은 결정론적 재시뮬레이션. 재생/일시정지/0.25×~4× 배속/카메라 변경(체이스, TV, 오빗, 콕핏)/플레이어 선택. 같은 게임 버전에서만 재생 가능. 보관 7일.
- 날씨(P3): 맑음/흐림/비/젖은 노면. 도입 시 타이어(인터미디어트/웨트 추가), 제동, 마찰, 시야 변경. 지금은 구현하지 않는다.

# PART 10. 네트워크 명세

## 10.1 서버 룸 상태 머신

`LOBBY_WAIT → TRACK_REVEAL → PREP → QUALI_COUNTDOWN → QUALIFYING → GRID → COUNTDOWN → RACE → FINISH → RESULT → CLOSED` (§9.1). 모든 전환은 서버가 틱 번호로 결정하고 `s2c_phase_changed`로 통지.

## 10.2 연결

- 매치 배정 시 백엔드가 `{host, port, match_token}`을 클라에 푸시. 클라가 ENet 접속 후 `c2s_join(match_token, protocol_version)`. 서버는 백엔드 서명(HMAC-SHA256) 검증.
- 채널: 0 = 신뢰성(제어/세팅/이벤트), 1 = 비신뢰·순서(입력/스냅샷).
- 틱 레이트: 서버 시뮬 120 Hz, 입력 60 Hz, 스냅샷 30 Hz.
- 프로토콜 버전 불일치 시 접속 거부.

## 10.3 메시지

| 방향 | 메시지 | 채널 | 필드 / 크기 |
|---|---|---|---|
| C→S | `c2s_join` | 0 | token, version |
| C→S | `c2s_setup_submit` | 0 | 파츠 9개 ID, 슬라이더 5, 모드 4, 타이어, 스킨 ID. 서버가 보유/범위/해금 검증 |
| C→S | `c2s_ready` | 0 | — |
| C→S | `c2s_input` | 1 | 최신 틱, 입력 3프레임 중복 전송. 프레임당 8 B (tick u32, throttle u8, brake u8, steer i8, buttons u8) → 패킷 약 30 B, 60 Hz |
| C→S | `c2s_pit_plan` | 0 | 컴파운드, 수리 플래그 |
| C→S | `c2s_reset_request` | 0 | — |
| S→C | `s2c_phase_changed` | 0 | 상태, 시작 틱, 트랙 ID, 시드 |
| S→C | `s2c_snapshot` | 1 | 서버 틱, ack된 마지막 입력 틱, 차량별 상태 |
| S→C | `s2c_event` | 0 | 랩 완료, 섹터 기록, 충돌, 피트 시작/종료, DNF, 순위 변화 |
| S→C | `s2c_qualifying_update` | 0 | 순위표 |
| S→C | `s2c_result` | 0 | 최종 순위, 기록, 분석 데이터, ELO 변화 |

**차량 스냅샷 (약 34 B)**: x,z (float32×2), 요 (u16), 속도 u,v (i16×2, 0.05 m/s), 요레이트 (i16), 조향 (i8), 스로틀/브레이크 (u8×2), 기어 (u8), 타이어 평균 마모 (u8), 에너지 (u8), 존 체력 8개 (nibble 4 B 요약), 플래그 (u16), 진행도 (u32 cm), 랩 (u8).
8대 + 헤더 ≈ 300 B × 30 Hz ≈ **9 kB/s 다운**, 업 ≈ 2 kB/s.

## 10.4 클라이언트 예측 / 재조정

1. 클라는 매 입력 틱 즉시 로컬 시뮬(예측)하고, 입력과 결과 `VehicleState`를 링 버퍼(256틱)에 보관.
2. 서버 스냅샷 수신: `ack_tick`의 저장 상태와 서버 상태를 비교.
3. 오차 처리:
   - 위치 오차 < 0.05 m, 속도 오차 < 0.2 m/s: 무시.
   - 그 이상: 서버 상태로 되돌려 `ack_tick+1 ~ 현재`의 입력을 재시뮬레이션(재조정).
   - 시각 보정: 렌더 오프셋을 100 ms에 걸쳐 감쇠. 오차 > 3 m이면 즉시 스냅.
4. 원격 차량: 스냅샷 보간, 보간 지연 100 ms(스냅샷 3개). 스냅샷 누락 시 최대 150 ms까지 속도/요레이트 외삽.
5. 로컬 예측 시 원격 차량은 보간된 위치를 고정 장애물로 취급(차량 간 충돌은 서버 판정을 따름).

## 10.5 네트워크 충돌 보정 (§90)

- 충돌은 **서버만 확정**. 클라이언트는 충돌 직전 근접 시 시각 보정으로 부드럽게 표시.
- 핑 공정 충돌(§6.11): 접촉 쌍 중 RTT > 120 ms가 있으면 임펄스 ×0.6, 손상 ×0.5.
- 서버 입력 버퍼: 클라 입력은 서버 수신 틱에 맞춰 최대 6틱(50 ms) 지터 버퍼 후 적용. 입력 지연이 길면 마지막 입력 유지.
- 기본 보호: Start Protection(§6.11), 피트/리셋 고스트.
- 고핑 시뮬레이션 테스트 필수: RTT 40/120/250 ms, 패킷손실 0/3/10%에서 8대 레이스 완주 및 이상 충돌 로그 확인(§15.4).
- RTT > 250 ms가 10 s 지속되면 경고, 20 s 지속되면 네트워크 이탈 처리.

## 10.6 서버 판정 / Anti-Cheat (§89, §92)

서버가 위치, 속도, 충돌, 랩, 순위, 완주, ELO를 판정한다. 클라는 입력만 신뢰 대상.

| 검증 | 임계값 |
|---|---|
| 입력 값 범위 | throttle/brake ∈ [0,1], steer ∈ [−1,1], 범위 밖 폐기 |
| 입력 빈도 | 70 패킷/s 초과 시 경고, 지속 시 연결 해제 |
| 결정론 불일치 | 클라가 보고한 체크섬(1 s마다)과 서버 상태 불일치가 10회 연속이면 플래그 |
| 속도 | 직선 속도 > 400 km/h 불가능, > 이론 최대(세팅 기준) ×1.05 시 플래그 |
| 랩타임 | 트랙 기준 랩타임 하한(AI 최대 세팅 최적 주행) × 0.97 미만이면 무효 + 플래그 |
| 이동 거리 | 랩당 이동 거리 < 트랙 길이 × 0.995 (체크포인트 누락) 시 무효 |
| 세팅 | 보유하지 않은 부품, 범위 밖 슬라이더, 미해금 모드는 서버가 거부 |
| 봇 의심 | 입력 패턴 분산이 인간 분포 하한(해상도별) 미만이고 랩타임 편차 < 0.05 s가 5랩 이상 지속 |

플래그된 매치는 입력 로그 + 시드를 보관(30일)해 재현 검증. 단계: 경고 → ELO 무효 → 일시 정지 → 영구 정지. 제재 결정은 자동 플래그 + 수동 검토.

# PART 15. 검증 인프라 · 수용 기준

AI가 "됐다"고 말하는 것과 실제 동작은 다르다. **Phase 1 시작 전에 자동 검증 수단부터 만든다.**

## 15.1 검증 도구

1. **GUT 단위 테스트**: 물리 수식, ELO, 스탯 집계, 매칭, 파서, 상태 머신.
2. **헤드리스 AI 드라이버**: 라인을 따라 자율 주행하며 랩타임 기록. `godot --headless`.
3. **랩타임 회귀**: 물리/세팅 수정 후 AI 드라이버 랩타임이 **±0.5 s 또는 ±0.6%**(큰 쪽)를 벗어나면 실패.
4. **파라미터 스윕**: 세팅 조합별 랩타임 표 자동 생성(`docs/balance/`), §7.13 검증.
5. **스크린샷 캡처**: 고정 카메라 프레임 캡처(`tools/screenshot.gd`)로 시각 회귀 확인.
6. **데이터 검증**: `tools/validate_data.py` — JSON 스키마, 아키타입 델타 합 0, 참조 무결성, i18n 키 누락.
7. **코딩 수칙 린트**: 주석 금지, 네이밍, 매직 넘버, 파일/함수 크기 (`lint_no_comments.py`, `lint_style.py`).
8. **사람의 역할**: 위가 잡지 못하는 단 하나, **"운전이 재미있는가"** 를 판정한다.

## 15.2 `tools/check.sh` (모든 커밋의 관문)

순서: 린트 → 데이터 검증 → GUT 전체 → Go 테스트(백엔드가 있는 경우) → 랩타임 회귀(core/data 변경 시). 하나라도 실패하면 종료 코드 ≠ 0.
