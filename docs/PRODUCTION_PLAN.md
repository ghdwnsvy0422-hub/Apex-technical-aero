# PART A. 기술 스택

## A-1. 게임 엔진: **Godot 4.4 + GDScript**

### 왜 Godot인가 (100% 바이브 코딩 기준)

바이브 코딩에서 엔진 선택의 유일한 기준은 **"AI가 텍스트만으로 게임 전체를 만들 수 있는가"** 이다.

| 항목 | Godot 4 | Unity | Unreal 5 |
|---|---|---|---|
| 씬 파일 포맷 | `.tscn` — **사람이 읽고 쓰는 텍스트** | `.unity` YAML + GUID 지옥 | `.umap` **바이너리** |
| 리소스/머티리얼 | `.tres` — 텍스트 | `.mat` YAML + meta 파일 쌍 | 바이너리 애셋 |
| AI가 씬을 직접 생성 | ✅ 가능 | ⚠️ GUID 수동 관리 필요, 깨지기 쉬움 | ❌ 사실상 불가 |
| 스크립트 컴파일 | 불필요 (GDScript) | C# 컴파일 필요 | C++ 빌드 or Blueprint(바이너리) |
| 헤드리스 실행/테스트 | `--headless` 기본 지원 | 복잡 | 무거움 |
| 전용 서버 빌드 | 공식 headless export | 별도 세팅 | 무거움 |
| 엔진 용량/반복 속도 | ~100MB, 즉시 실행 | 수 GB | 수십 GB |

Unreal은 Blueprint가 **바이너리**라 AI가 손댈 수 없고, Unity는 프리팹/씬의 GUID 참조 구조 때문에 AI가 만든 씬이 깨지기 쉽다. **Godot만 "게임 전체가 git diff로 보이는" 엔진이다.**

### 왜 GDScript인가 (C# 아님)

- 컴파일 단계가 없어 수정 → 실행 루프가 1초 이내. 바이브 코딩의 반복 속도가 곧 개발 속도다.
- 파일 1개 = 클래스 1개, 씬 노드에 직접 붙는 구조라 AI가 파일 경계를 헷갈리지 않는다.
- 성능 병목이 실제로 측정되면 그 부분만 나중에 GDExtension(C++/Rust)으로 교체한다. **선제적 최적화는 하지 않는다.**

### 물리: **Jolt Physics (Godot 4.4 내장)**

- Godot 4.4부터 Jolt가 엔진에 통합됨. 별도 설치 불필요.
- 차량 물리는 Godot의 `VehicleBody3D`를 **사용하지 않는다.** 그 노드는 아케이드용이고 타이어 슬립/마모/다운포스 모델을 넣을 수 없다.
- 대신 `RigidBody3D` + **커스텀 레이캐스트 서스펜션 + Pacejka 간이 타이어 모델**을 직접 구현한다. PRD의 §24 차량 스탯 12종, §29 타이어 마모, §27 트레이드오프는 커스텀 모델 없이는 구현 불가능하다.

### 네트워크: **ENet (Godot 내장) + Godot 헤드리스 전용 서버**

- PRD §89(서버 권위 판정)를 만족하려면 서버가 **클라이언트와 100% 동일한 물리**를 돌려야 한다.
- 같은 GDScript 물리 코드를 헤드리스 Godot 서버에서 실행 → 클라/서버 물리 불일치가 구조적으로 발생하지 않는다. 이게 Godot 선택의 가장 큰 실익이다.
- 클라이언트 예측 + 서버 재조정(reconciliation) + 원격 차량 스냅샷 보간.

### 백엔드(계정/ELO/매칭): **Go + PostgreSQL**

- 게임 서버(Godot)와 분리. 매칭/ELO/프로필은 실시간 물리와 무관하므로 별도 서비스.
- Go 선택 이유: 단일 바이너리 배포, 동시성 처리 단순, AI가 작성한 코드의 컴파일 에러가 즉시 잡힘(= 바이브 코딩에서 자기 검증이 쉬움).
- Redis: 매칭 큐 + 세션 상태.

### 최종 스택

```
클라이언트     Godot 4.4 / GDScript / Jolt
게임 서버      Godot 4.4 헤드리스 (동일 코드베이스, 서버 권위)
백엔드         Go + PostgreSQL + Redis
전송           ENet(UDP, 게임) / HTTPS+WebSocket(메타)
배포           Docker, 게임서버 리전별 인스턴스
검증           GUT(단위테스트) + 헤드리스 AI 드라이버 자동 랩타임 회귀
```

# PART B. 애셋 전략 — "그리지 않고 만든다"

100% 바이브 코딩에서 가장 큰 함정은 **3D 모델링/텍스처링**이다. AI는 .blend나 .png를 직접 만들지 못한다.
따라서 **모든 애셋을 "코드로 생성되는 것" 또는 "CC0 라이브러리에서 가져오는 것" 둘 중 하나로만 정의한다.**

## B-1. 트랙 — 절차적 생성 (핵심 전략)

트랙을 3D 모델링하지 않는다. **텍스트 DSL로 서술하고 코드가 메시를 만든다.**

```json
{
  "name": "Aurora Speedway",
  "type": "high_speed",
  "segments": [
    { "straight": 850 },
    { "corner": { "angle": -90, "radius": 120, "banking": 3 } },
    { "straight": 320 },
    { "corner": { "angle": 45, "radius": 260, "elevation": 8 } },
    { "chicane": { "width": 14, "length": 90 } }
  ],
  "width": 15.0,
  "pit_entry": 12,
  "drs_zones": []
}
```

이 JSON → `Curve3D` → 노면/커브스톤/런오프/가드레일 메시 + 충돌체 + 레이싱 라인 + 섹터 분할까지 **전부 코드가 생성**한다.

이 방식의 실익:
- 트랙 1개 추가 = JSON 파일 1개 작성 (**토큰 소모 매우 적음**). PRD §82 라이브 콘텐츠 시즌이 사실상 공짜가 된다.
- 트랙 밸런싱이 숫자 수정으로 끝난다.
- AI가 "코너를 조금 더 조이자"는 피드백을 즉시 반영 가능.

## B-2. 차량 — 3단계 점진 교체

| 단계 | 방식 | 시점 |
|---|---|---|
| 1차 | 프리미티브 조합 (BoxMesh 섀시 + CylinderMesh 휠) | Phase 1~2 |
| 2차 | 코드 생성 메시 (섀시/윙/디퓨저를 `SurfaceTool`로 절차 생성, 부품별 파츠 분리) | Phase 3 |
| 3차 | CC0 로우폴리 모델 교체 (Kenney, Quaternius, Poly Pizza) | Phase 6 |

**중요**: 부품 시스템(§23)의 시각적 표현은 처음부터 **"파츠 노드 스왑"** 구조로 설계한다. 그래야 3차에서 모델만 갈아끼우면 되고 로직 재작성이 없다.

## B-3. 리버리/스킨 — 셰이더 파라미터 (텍스처 파일 없음)

PRD §75 리버리는 **PNG를 만들지 않는다.** 절차적 셰이더로 처리한다.

```
livery = {
  base_color, accent_color, secondary_color,
  pattern: stripe | split | gradient | geometric | flame,
  pattern_scale, pattern_angle, metallic, roughness,
  decal_slots: [...]
}
```

- 리버리 1종 = JSON 몇 줄. 시즌마다 수십 종 추가해도 용량/토큰 부담 0에 가깝다.
- 성능에 영향 없음(§78) → 순수 시각 데이터로 분리하기도 쉽다.
- 나중에 아티스트가 합류하면 데칼 텍스처만 슬롯에 얹으면 된다.

## B-4. 환경/월드

- 하늘: Godot `ProceduralSkyMaterial` + 시간대 프리셋
- 지형: 트랙 스플라인 기반 절차적 오프트랙 메시
- 관중/건물/광고판: 프리미티브 + `MultiMeshInstance3D` 인스턴싱 (스플라인 따라 자동 배치)
- 조명: 단일 DirectionalLight + SDFGI/VoxelGI, 후처리는 Godot `WorldEnvironment`

## B-5. UI

- 100% Godot `Control` 노드 + `Theme` 리소스(.tres, 텍스트) → AI가 완전히 제어 가능
- 아이콘: 인라인 SVG 또는 폰트 아이콘 (Material Symbols, Apache 2.0)
- 폰트: Rajdhani / Inter (OFL) — 모터스포츠 톤에 맞는 무료 폰트

## B-6. 사운드

- 우선순위 최하위. Phase 6까지 무음 또는 플레이스홀더로 진행.
- 엔진음: RPM 기반 절차적 합성(피치 시프트 + 레이어) 또는 CC0 샘플(freesound.org)
- UI/충돌음: Kenney Audio Pack (CC0)

## B-7. 애셋 라이선스 원칙

**CC0 / OFL / Apache 2.0만 사용한다.** 상업적 라이브 서비스가 목표이므로 라이선스 오염을 처음부터 차단한다. 모든 외부 애셋은 `docs/ASSET_CREDITS.md`에 출처를 기록한다.

# PART C. 바이브 코딩 검증 루프 (가장 중요한 인프라)

AI가 "됐습니다"라고 말하는 것과 실제로 되는 것은 다르다. Phase 1 시작 전에 **자동 검증 수단**부터 만든다. 이게 없으면 이후 모든 단계가 추측이 된다.

1. **GUT 단위 테스트** — 물리 수식, ELO 계산, 스탯 집계 등 순수 로직
2. **헤드리스 AI 드라이버** — 레이싱 라인을 따라 자율 주행하며 랩타임을 기록. `godot --headless` 로 실행.
3. **랩타임 회귀 테스트** — 물리 수정 후 AI 드라이버 랩타임이 ±0.5초를 벗어나면 경고. "물리를 고쳤는데 차가 못 달리게 됨"을 자동 감지.
4. **파라미터 스윕** — 세팅 값을 자동으로 훑으며 랩타임 표 생성 → PRD §27 트레이드오프가 실제로 작동하는지 수치로 증명.
5. **스크린샷 캡처** — 고정 카메라 프레임 캡처로 시각적 회귀 확인.
6. **사람의 역할** — 위 5개가 잡지 못하는 단 하나, **"운전이 재미있는가"** 를 판정한다.

**개략 총 예산**: 대략 400만~600만 토큰 규모. 단, 실제 소모의 대부분은 신규 코드 작성이 아니라 **튜닝 반복(1.8, 3.9)과 버그 수정**에서 발생한다.

### 토큰 절약 원칙

1. **PRD와 이 문서를 리포에 둔다** — 매 세션 컨텍스트 재설명 불필요.
2. **`CLAUDE.md`에 코딩 규약을 명시** — 스타일 지적 왕복 제거.
3. **자동 검증(PART C)에 선투자** — "고쳤는데 다른 게 깨짐"의 발견을 사람이 아닌 테스트가 한다. 이게 최대 절약 요인.
4. **데이터는 코드가 아니다** — 트랙/부품/리버리는 JSON. 콘텐츠 추가 비용을 상수로 만든다.
5. **한 세션 = 한 단계** — 여러 단계를 섞으면 컨텍스트가 오염되고 재작업이 늘어난다.
