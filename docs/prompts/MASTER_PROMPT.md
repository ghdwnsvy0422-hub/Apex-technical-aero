# MASTER_PROMPT — 최초 1회 전체 분석

사용 시점: Apex 저장소에서 Claude에게 개발을 맡기는 **첫 세션** 1회. 이후 세션은 `WORK_PROMPT_TEMPLATE.md`를 쓴다.
상시 규칙은 `CLAUDE.md`에 있다. 이 문서는 규칙을 반복하지 않고 **이 세션이 해야 할 일**만 정의한다.

아래 `---` 이후를 Claude에게 붙여 넣는다.

---

너는 Apex 프로젝트의 수석 개발자다. 이번 세션의 목적은 **분석과 계획**이다. 코드를 작성하거나 게임 기능을 구현하지 않는다.

## 이번 세션의 산출물

1. 저장소 분석 결과 보고
2. `docs/DEVELOPMENT_STATUS.md` §10 요구사항 추적 표 작성
3. 기술적 위험 및 설계상 문제 목록
4. 단계별 실행 계획 (작업 순서, 완료 조건, 검증 기준)
5. `docs/DEVELOPMENT_STATUS.md` 갱신 (이 문서 외 어떤 파일도 수정하지 않는다)

## 절대 하지 말 것

- 게임 코드, 데이터, 테스트, 도구 스크립트 수정 또는 추가
- `CLAUDE.md`, `PRD.md`, `PRODUCTION_PLAN.md`, `handoff.md` 수정 (문제를 발견하면 보고만 한다)
- 계획 승인 전에 구현 시작
- 문서에 근거 없는 수치·구조를 확정 (모르면 "미결"로 기록하고 질문 목록에 올린다)
- 확인하지 않은 항목을 `완료`로 기록

## 절차

### 1. 읽기 (이 순서)

`CLAUDE.md` → `handoff.md` → `docs/DEVELOPMENT_STATUS.md` → `docs/PRD.md` → `docs/PRODUCTION_PLAN.md`

읽으면서 문서끼리 어긋나는 곳(수치, 구조, 단계 번호, 규칙)을 목록으로 만든다.

### 2. 저장소 조사

- `git status`, `git log --oneline`, 현재 브랜치, `origin/main`과의 차이
- 디렉터리별 파일 수와 역할: `game/core`, `game/ai`, `game/client`, `game/track`, `game/data`, `game/ui`, `game/net`, `game/server`, `game/tests`, `tools`, `backend`
- 진입점과 오토로드: `game/project.godot`, `game/main.gd`, `game/main.tscn`
- 데이터 파일과 그것을 검증하는 코드(`DataRegistry`)가 짝을 이루는지
- 빈 디렉터리(`.gitkeep`만 있는 곳)와 계획서상 해당 단계
- 문서가 말하는 상태와 코드가 일치하는지: 각 `완료` 주장마다 대응하는 코드와 테스트를 찾는다

### 3. 실행해서 확인

```bash
./tools/install_godot.sh
./tools/check.sh
./tools/godot.sh --headless --path game --quit-after 120
```

- 출력 전체를 읽는다. 종료 코드만 보지 않는다. 경고(Jolt 경고, 고아 노드 등)와 실패를 모두 기록한다.
- `./tools/sweep.sh`는 수 분이 걸리므로 필요하다고 판단될 때만 돌리고, 돌렸다면 결과를 기록한다.
- 실행할 수 없는 것(디스플레이, 사람 주행 등)은 "미확인"으로 기록한다.

### 4. 요구사항 추적

`docs/DEVELOPMENT_STATUS.md` §10 표를 채운다.

- PRD를 절 단위로 훑어 요구사항을 묶고, 각각에 제작 계획 작업 번호와 구현 위치(파일), 상태, 검증 근거(테스트 이름 또는 명령)를 적는다.
- 상태는 `완료` / `부분` / `미착수` / `미확인`. 테스트나 실행으로 확인하지 않았으면 `미확인`이다.
- PRD에 있으나 제작 계획에 대응 작업이 없는 요구사항, 제작 계획에 있으나 PRD 근거가 없는 작업은 별도로 표시한다.
- PRD가 "후속 결정"으로 남긴 항목(§6 K-factor, §51 DRS, §52 에너지 존 등)은 임의로 정하지 말고 "미결"로 표시한다.

### 5. 구조와 의존성

- 모듈 간 의존 방향을 정리한다. 특히 `game/core`가 렌더링/입력/씬 트리에 의존하지 않는지 실제 코드에서 확인한다.
- Phase 2 이후 작업이 현재 코드의 어떤 부분에 의존하는지 정리한다: 차량 상태의 직렬화 가능성, 입력이 값으로 주입되는지, 시간이 틱 기반인지, 난수 사용 위치.
- 선행 조건 그래프(작업 A가 끝나야 B 가능)를 만든다.

### 6. 기술적 위험 및 설계 문제 발견

다음 영역마다 코드를 근거로 점검하고, 문제는 "증상 / 근거(파일, 줄, 로그) / 영향 / 확인 방법" 형식으로 적는다. 추측이면 추측이라고 쓴다.

- **차량 물리**: 타이어 접지/마찰, 다운포스·항력 결합, 마모, 충돌, 120Hz 고정 틱 가정, `handoff.md` §6의 함정이 코드와 테스트로 지켜지는지
- **주행감**: 자동 검증이 보지 못하는 것(재미, 조종감)을 어떻게 사람이 판정할지
- **네트워크 (미래)**: 동일 코드가 동일 결과를 보장하지 않는다는 전제로 — 서버 권위 구조, 클라이언트 예측과 서버 상태 보정의 분리, 현재 `RigidBody3D`/Jolt 기반 상태를 저장·복원·재시뮬레이션할 수 있는지, 입력이 값으로 주입되는 구조가 유지되는지
- **트랙/AI**: 트랙 데이터 검증 범위, 진행도 판정의 전제(`handoff.md` §6.11), AI가 못 다루는 세팅
- **검증 인프라**: 게이트가 놓치는 종류의 회귀, 랩타임 기준값의 취약성, CI 실제 실행 여부
- **백엔드 (미래)**: 현재 단계에서 도입이 불필요함을 확인하고, 도입 시점과 선행 조건만 기록

### 7. 실행 계획 수립

`PRODUCTION_PLAN.md`의 단계 순서를 기준으로 하되, 아래 원칙을 지킨다.

- 초기 우선순위는 주행감과 재미 검증이다. Phase 1 게이트(사람 판정) 이전에 매칭, 랭킹, 상점, 백엔드를 계획에 "착수 가능"으로 올리지 않는다.
- 각 작업마다: 목표, 완료 조건(실행 가능한 명령 또는 측정값), 검증 기준, 선행 작업, 예상 영향 범위, 위험을 적는다.
- 사람의 개입이 필요한 지점(주행 판정, 승인)을 명시한다.
- 한 작업은 한 세션에 끝낼 수 있는 크기로 나눈다. 크면 쪼갠다.
- 계획서와 현재 코드가 충돌하면 어느 쪽도 고르지 말고 선택지와 영향을 나열한다.

### 8. 기록

`docs/DEVELOPMENT_STATUS.md`를 갱신한다: §3 작업 현황 보정, §6 버그, §7 위험, §8 우선순위, §10 요구사항 추적, §11 변경 이력. 실제로 확인한 근거만 쓴다.

### 9. 커밋

문서만 바꿨으므로 `check.sh`는 필요 없다. 변경 파일이 `docs/DEVELOPMENT_STATUS.md` 하나인지 `git diff --stat`으로 확인하고 커밋한다.

## 보고 형식

1. **요약**: 현재 단계, 가장 큰 위험 3개, 다음에 해야 할 일 1줄
2. **조사 결과**: 문서-코드 불일치, 실행 결과(통과/실패/경고), 확인하지 못한 것
3. **요구사항 추적 요약**: 완료/부분/미착수/미확인 개수와 공백 항목
4. **위험 목록**: 심각도 순
5. **실행 계획**: 작업별 표
6. **사용자에게 묻는 질문**: 결정이 필요한 항목만, 선택지와 권장안 포함

## 종료 조건과 다음 세션 이어가기

- 계획을 보고한 뒤 **멈추고 사용자 승인을 기다린다.** 승인 없이 구현하지 않는다.
- 다음 세션은 `docs/DEVELOPMENT_STATUS.md`만 읽어도 이어갈 수 있어야 한다. 그래서 상태, 마지막 검증, 다음 작업과 완료 조건을 빠짐없이 적는다.
- 승인된 첫 작업은 `STAGE_0_1_PROMPT.md`, 그 이후는 `WORK_PROMPT_TEMPLATE.md`로 진행한다.
