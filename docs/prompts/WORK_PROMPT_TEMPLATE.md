# WORK_PROMPT_TEMPLATE — 개별 개발 작업 지시 템플릿

사용 시점: `MASTER_PROMPT` 승인과 `STAGE_0_1_PROMPT` 이후의 **모든 개발 작업**. 작업 하나당 세션 하나.
사용법: 아래 `---` 이후를 복사하고 `[작업 정의]`의 빈칸만 채워서 Claude에게 붙여 넣는다. 절차 본문은 수정하지 않는다.

---

너는 Apex 프로젝트의 수석 개발자다. 아래 [작업 정의]의 작업 **하나**를 수행한다. 상시 규칙은 `CLAUDE.md`를 따른다.

## [작업 정의]

| 항목 | 내용 |
|---|---|
| 작업 번호 | (예: `PRODUCTION_PLAN` Phase 2.1) |
| 목표 | (한 문장) |
| 완료 조건 | (실행 가능한 명령 또는 측정값으로. 예: `./tools/check.sh` 통과 + 새 테스트 N개 + 특정 지표 ≤ 값) |
| 범위 (이 작업에 포함) | (건드려도 되는 디렉터리/파일/기능) |
| 제외 (이 작업에서 하지 않음) | (명시적으로 금지할 것) |
| 관련 문서 | (`PRD.md` §, `PRODUCTION_PLAN.md` 작업 번호, `handoff.md` §) |
| 사람이 확인할 것 | (있으면. 예: 직접 주행 후 판정) |

## 범위 규칙

- 작업 정의에 없는 기능, 추상화, 설정, 파일을 추가하지 않는다. 필요하다고 판단되면 구현하지 말고 보고한다.
- 범위 밖에서 발견한 버그와 개선점은 고치지 않고 `docs/DEVELOPMENT_STATUS.md`에 기록한다.
- 기존 기능을 삭제하거나 동작을 바꾸지 않는다. 불가피하면 먼저 이유와 영향을 보고하고 승인을 받는다.
- 문서에 근거 없는 수치/정책/구조를 정해야 하는 상황이면 멈추고 질문한다.

## 절차

각 단계를 순서대로 수행하고, 끝낼 때 어느 단계까지 했는지 보고에 포함한다.

### 1. 현재 프로젝트 상태 확인

- `git status`, `git log -5`, 현재 브랜치. 작업 트리가 깨끗하지 않으면 원인을 파악하고 보고한다.
- `docs/DEVELOPMENT_STATUS.md`를 읽고 이 작업의 선행 작업이 `완료`인지 확인한다. 아니면 중단하고 보고한다.
- `./tools/check.sh`를 **작업 시작 전에** 실행해 기준선을 기록한다 (테스트 수, 프로브 결과, 랩타임). 이미 실패하면 이 작업을 시작하지 말고 보고한다.

### 2. 관련 문서와 기존 코드 분석

- `[관련 문서]`를 읽는다. 작업에 영향을 주는 `handoff.md` §6의 함정을 모두 확인한다.
- 수정 대상 파일과 그 호출처, 관련 테스트를 읽는다. 읽지 않은 코드는 수정하지 않는다.
- 문서와 코드가 어긋나면 어느 쪽이 맞는지 임의로 정하지 말고 기록한다.

### 3. 작업 목표와 완료 조건 파악

- 목표와 완료 조건을 자기 말로 다시 쓴다. 완료 조건이 모호하거나 측정할 수 없으면 구현 전에 질문한다.
- "무엇이 되면 끝인가"를 실행 가능한 검증 명령으로 바꾼다.

### 4. 의존성 및 영향 범위 분석

- 수정할 심볼을 쓰는 모든 곳을 `grep`으로 찾는다.
- 영향 가능성을 점검한다 (해당하는 것만):
  - `game/core` 변경 → 헤드리스/서버 실행 가능성, `Input.*`/씬 트리 의존 금지
  - 물리 변경 → 랩타임 기준값(`BASELINE_LAP_S`), 물리 프로브, AI 드라이버, 성능 엔벌로프
  - 데이터 변경 → `DataRegistry` 검증기, 스키마 버전
  - 네트워크 관련 → 서버 권위, 클라이언트 예측과 서버 보정의 분리, 동일 코드가 동일 결과를 보장하지 않는다는 전제
  - 트랙 변경 → 닫힘 검증, 진행도 판정 전제(`handoff.md` §6.11)
- 영향받는 기존 테스트 목록을 만든다.

### 5. 구현 계획 수립

- 변경할 파일, 추가할 테스트, 실행할 검증 명령을 순서대로 적는다.
- 계획이 범위를 넘으면 줄이거나 사용자에게 확인한다.
- 큰 설계 선택이 있으면 선택지와 권장안을 보고하고 승인을 받은 뒤 진행한다.

### 6. 코드 작성 및 수정

- 최소 변경 원칙. 필요한 줄만 바꾼다. 불필요한 리팩터링, 이름 변경, 파일 이동을 하지 않는다.
- **새로 쓰거나 수정하는 코드에 주석을 달지 않는다.** 이름과 함수 분리로 의도를 드러낸다.
- 정적 타입 필수, `print()` 대신 `Log`, 식별자는 영어.
- 새 데이터 종류를 만들면 검증기도 함께 만든다.
- 가능하면 새 동작마다 테스트를 먼저 또는 함께 추가한다.

### 7. 실제 실행 및 테스트

- `./tools/check.sh`를 실행하고 출력을 끝까지 읽는다. 종료 코드만 보지 않는다.
- 변경 성격별 추가 검증:
  - 시각적 변경: `./tools/screenshot.sh /tmp/shot.png 26`으로 캡처해 눈으로 확인한다.
  - 물리/세팅 변경: 프로브와 랩타임 회귀 결과를 기준선과 비교한다. 밸런스 판단이 필요하면 `./tools/sweep.sh`.
  - 주행감 변경: 자동 검증으로 "재미"를 판정하지 않는다. 사람이 확인할 항목으로 남긴다.
- 실행할 수 없는 검증은 "미검증"으로 기록한다.

### 8. 오류 수정과 재검증

- 실패하면 추측으로 고치지 않는다. 재현 → 로그/값으로 원인 특정 → 수정 → **검증을 처음부터 다시** 실행한다.
- 테스트를 약화·삭제·스킵하거나 허용 범위를 넓혀서 통과시키지 않는다.
- 랩타임 기준값을 옮겨야 한다면, 물리를 의도적으로 바꾼 것이 맞는지 먼저 확인하고 커밋 본문에 사유를 쓴다.
- 같은 원인으로 3번 실패하면 멈추고 현재까지의 증거와 가설을 보고한다.

### 9. 기존 기능에 대한 회귀 영향 확인

- 1단계에서 기록한 기준선과 비교한다: 테스트 수가 줄지 않았는지, 프로브가 모두 PASS인지, AI 랩타임이 기준값 범위 안인지, 경고/오류 출력이 새로 생기지 않았는지.
- 4단계의 영향 테스트 목록을 확인한다.
- `git diff --stat`으로 변경 파일이 계획과 일치하는지 본다. 계획에 없는 파일이 있으면 되돌리거나 사유를 보고한다.

### 10. `docs/DEVELOPMENT_STATUS.md` 업데이트

- §2 마지막 검증: 일시, 커밋, 실행한 명령, 결과(통과 개수, 주요 수치, 경고)
- §3 작업 현황: 이 작업의 상태. 사람 확인이 남았으면 `완료`가 아니라 `미확인` 또는 `진행 중`
- §6 버그 / §7 위험: 새로 발견한 것 (범위 밖 항목 포함)
- §8 다음 작업: 우선순위 재조정
- §11 변경 이력
- 새로 알게 된 함정과 설계 이유는 `handoff.md` §6에 추가한다 (코드에 주석을 달 수 없기 때문).
- 근거 없이 `완료`로 쓰지 않는다.

### 11. 커밋, 다음 작업 제안, 완료 보고

- 코드 변경은 논리 단위로 커밋한다 (영어 명령형 제목, 본문에 **왜**). `check.sh` 통과 후에만 커밋한다. 문서 갱신은 같은 커밋 또는 직후 커밋.
- 지정된 브랜치에만 푸시한다.
- 완료 보고 형식:

```
작업: <번호> <목표>
결과: 완료 | 부분 완료 | 중단   (완료 조건 항목별로 충족/미충족)
변경: 파일 목록과 한 줄 요약
검증: 실행한 명령 → 결과 (통과 수치, 경고 포함)
회귀: 기준선 대비 변화
미검증/미확인: 확인하지 못한 것과 이유
범위 밖 발견: 기록한 항목
사람이 할 일: (있으면)
다음 작업 제안: DEVELOPMENT_STATUS §8 기준 1~2개와 이유
```

실패했거나 일부만 된 것은 있는 그대로 쓴다. 테스트하지 않은 기능을 완료했다고 보고하지 않는다.
